Plugin Host

Your own CLAP and VST3 plugins, loaded on your machine and played in your browser. Render a selection, move the knobs, keep the WAV. Nothing is uploaded anywhere.

Read this first

A browser cannot load a .clap, a .vst3 or a .component.

Those are native shared libraries. No browser has an API that will open one, there is no flag for it, and there is no clever way round it — the sandbox exists precisely to stop a web page running native code off your disk. Anything claiming to run your plugin collection inside a tab is either running something else entirely, or has a local program doing the real work and is not telling you.

So this page is not the thing. pluginhost is: a small program you run on your own machine. It opens the plugin, and it serves the page that drives it. It is under sixty kilobytes, it talks to nothing but your browser, and it is about two thousand lines of C you could read in an afternoon.

Run it

You need a C compiler, make and git — on a Mac that means Xcode's command line tools, which you probably already have. 

$ git clone https://github.com/lucidsoup/lucidsoup.github.io.git
$ cd lucidsoup.github.io/pluginhost
$ make
$ ./pluginhost

make fetches two sets of plugin headers — CLAP's, which are MIT, and Steinberg's C binding for VST3, which is BSD — and builds one binary. Nothing else is downloaded and nothing is installed.

It prints an address and opens it. If it did not, or you closed the tab:

Open pluginhost →

That only works while the program is running on this computer, and you will get a connection error otherwise. It is deliberately not reachable from anywhere else.

What it looks like

How it works

Pick a plugin, drop a sound on it, and drag across the waveform to choose a region. The plugin's own parameters appear as sliders — its names, its ranges, its readouts, not a guess at them. Move one and the selection re-renders in about a tenth of a second.

It renders rather than streams, which is a choice and not a shortcut. A plugin runs far faster than real time, so a passage comes back in a fraction of its own length, and what you keep at the end is a WAV rather than a performance you had to sit through and capture. Save it and drop it straight into the SP-404 converter to chop.

Two things it gets right that are easy to get wrong: a plugin that reports latency has it compensated, so what comes back lines up with what went in instead of being quietly shifted; and parameters are settled against silence before the audio starts, so a value lands where you put it instead of gliding up to it over the first few milliseconds.

Which plugins

FormatWorks
CLAP Yes A plain C interface in MIT headers, with no SDK and no licence to agree to. It was first for that reason, not because it is the most common.
VST3 Yes Easier than its reputation: the main SDK is C++ and dual-licensed, but Steinberg also publish a single BSD-licensed header describing the same interface in C, which is what this is built against.
AU Not yet macOS only, and it cannot be built or tested anywhere but a Mac — so it has to be done on the machine it runs on rather than guessed at.

It looks where each format is normally kept — ~/.clap and ~/.vst3 on Linux, ~/Library/Audio/Plug-Ins/ on a Mac — and anywhere else you point it with --scan. Plenty of plugins now ship a CLAP build alongside their VST3, so it is worth checking what you already own.

Is it safe to run

It loads native code from your own disk, which is exactly what any DAW does. The care taken is proportionate to that:

  • It listens on 127.0.0.1 only, and there is no flag to change it.
  • Every call needs a token, freshly made each time it starts and written into the page as it is served — so it never reaches the address bar, your history, or a referer header.
  • A request from another website is refused, so a page you have open elsewhere cannot drive it even knowing the port.
  • It keeps nothing between requests and writes nothing to disk.

There is also a reason the address is 127.0.0.1 and not this site. Safari will not let an https:// page reach a local program at all, and Chrome began asking permission before it would. Serving the page from the program that answers it sidesteps both, and behaves the same in every browser.

The source

Four files of C and one page, in pluginhost/. It is tested against two plugins written to be measured: both compute a known result and declare a known latency, so a correct host hands back the input sample for sample. That is what the test suite checks, rather than whether the output merely sounds plausible.
